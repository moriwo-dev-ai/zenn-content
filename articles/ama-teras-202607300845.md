## 症状: 何を切り替えても、戻っている

自己進化型デスクトップAIエージェント AMA-teras([GitHub](https://github.com/moriwo-dev-ai/ama-teras))で、1週間にわたる連鎖障害が起きました。結論から書くと、原因は**設定読み込みの1行**です。この記事は、その1行に辿り着くまでの記録です。

症状は不可解でした。

- 設定画面でモデルプロバイダを Moonshot(Kimi)に切り替える → 動く
- ところが数日後、APIエラーで本体チャットが全停止
- 設定を見ると「Provider: Anthropic / Model: kimi-k3」という**謎の組み合わせ**に戻っている
- エージェントの自己進化ジョブは5連続で失敗。ログには一言だけ — 「エージェントが異常終了: error」

「切り替えたはずなのに戻っている」。ユーザー(私)は自分の操作ミスを疑い、もう一度切り替える。しばらく動く。そしてまた壊れる。この繰り返しでした。

## 手がかりゼロの原因: エラーの握りつぶし

調査を阻んだのは、進化ジョブのログに残る「異常終了: error」という文字列だけの報告でした。`error` って何だ。どのAPIが、何と言って断ったのか。何も分かりません。

コードを見ると、原因はすぐ分かりました。エージェントループはエラーイベントをちゃんと発行していたのに、進化ジョブ側のイベントハンドラが**テキストとツール実行のイベントだけ拾って、エラーイベントを捨てていた**のです。

```ts
emit: (e) => {
  if (e.kind === 'text_delta') lastText += e.text;
  if (e.kind === 'tool_start') log(`[job] tool: ${e.name}`);
  // ← e.kind === 'error' を誰も拾っていなかった
},
```

修正は20行です。エラーイベントをジョブログに記録し、例外メッセージにも実文言を付ける。それだけ。

## 修正した翌朝、ジョブが「自白」した

可観測化を入れて失敗ジョブを再走させると、今まで「error」としか言わなかったジョブが、初回のLLM呼び出しで即座にこう吐きました。

> 400 Your credit balance is too low to access the **Anthropic API**.

……Anthropic? 設定はMoonshotのはずです。接続テストを叩くと、確かにリクエストは `api.anthropic.com` に飛んでいる。**アプリの中では、設定がAnthropicに戻っている**。ディスク上の設定ファイルには `"provider": "moonshot"` と書いてあるのに、です。

ここまで来れば一直線でした。設定ファイルの読み込みコードがこれです。

```ts
if (rec['provider'] === 'anthropic' || rec['provider'] === 'openai') {
  merged.provider = rec['provider'];
}
// 'moonshot' は受理されず、既定値 'anthropic' が残る
```

数週間前、Moonshotを「正式プロバイダ」に昇格させたとき、切替UI・APIクライアント・キー管理・テストは全部更新したのに、**読み込み側のバリデーションだけ更新し漏れていた**。その結果、

1. ユーザーが Moonshot に切り替える(メモリ上は正しく切り替わる)
2. アプリを再起動する
3. 読み込み時に `'moonshot'` が黙って捨てられ、既定の `'anthropic'` に巻き戻る
4. モデルIDだけ `kimi-k3` が残り、AnthropicにKimiのIDを送り続ける
5. Anthropic側のクレジットが尽きた日、すべてが止まる

「切り替えたのに戻っている」の正体は、再起動のたびに発症する**サイレントな巻き戻し**でした。

## 学んだこと

**1. エラーの握りつぶしは、調査コストを後払いで爆発させる。** 実エラーには最初から「Anthropic API」「credit balance」と真犯人の名前が書いてありました。それを1週間見えなくしていたのは自分のコードです。可観測化の20行は、5連続のジョブ失敗と数日の調査より圧倒的に安い。

**2. 型検査は「受理リストの更新漏れ」を検出できない。** このコードはTypeScriptのstrictモードで型エラーゼロでした。`'moonshot'` を弾く挙動は型的には完全に正しい。機能追加のとき「書き込み側」は更新しても「読み込み側の受理リスト」を忘れる — この非対称は型では守れないので、**保存→再読込の往復テスト**で固定しました。

**3. 「黙って既定値に落とす」は最悪の失敗モード。** 不正な値を弾くこと自体は正しい設計です。ただし**黙って**弾くと、ユーザーには「操作したのに戻っている」という超常現象に見えます。せめてログに一行。できれば起動時に警告。

**4. 自己申告ではなく一次情報。** 「設定画面はMoonshotと表示している」は真実ではありませんでした。実際にどのURLへリクエストが飛んだか、という一次情報だけが真実でした。AMA-terasの設計原則「エージェントの成功報告を信用せず一次情報で裏取りする」が、今回は自分自身のアプリに刺さった形です。

## おまけ: 直った日のうちに、エージェントが道具を作った

プロバイダ巻き戻しを直した数時間後、止まっていた自己進化パイプラインが復活し、エージェントは「失敗ジョブの原因を要約する調査ツール」を自分で書き、隔離worktreeで型検査・テスト12件・実行スモークを通し、人間の承認を経て自分に組み込みました。**今回の障害の再発を、エージェント自身が調査できる道具**が最初の成果物になったのは、少し出来すぎな結末でした。
